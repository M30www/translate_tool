## D20 · 2026-10-25 · 实时启动器默认加 `--threshold 0.004`（并明确阈值上限）

**目的**：E11 里真机 OCR 产出率只有 17%（103 次触发只出 18 次新行），大量 OCR 白跑。用户要求只调参数、不动"超时丢弃"。

**改了什么**：`run_live_translate.bat` 的默认参数加 `--threshold 0.004`（原默认 0.002）。

**为什么只调到 0.004、不一次到位**
- 阈值是"整块区域的变化像素占比"，而**一条新聊天行只占其中的 0.3%~1%**（E8 实测新消息触发时的变化量就是这个量级）。
- 因此提到 0.8% 以上**很可能把真实新消息一起挡掉**——而召回是唯一不能丢的指标（当前 25/25）。
- 所以先走温和一档（0.2% → 0.4%），用下一轮真机数据验证召回是否仍满分；掉了就退回。
- **用户已明确不做"超时丢弃"**：免费引擎慢是已知成本，愿意等，不引入 `--translate-max-age`。

**怎么验证的**：`--replay` 确认参数被正确接收（启动行显示 `阈值=0.4%`），bat 仍为纯 ASCII（非 ASCII 字节 0），参数透传链路正常。

**遗留**
- 0.004 是否安全（召回不掉）需要真机数据确认（等 E12）。
- 收紧框选区域比调阈值更有效也更安全（区域里混进队伍列表与游戏画面，才是"画面一直动"的主因）。

## D19 · 2026-10-25 · T1：实时翻译通道（队列 + 翻译线程）

**目的**：把"离线翻译"变成"跑着就有译文"，这是从"能看"到"能用"的关键一跳，也是验证这个小玩具能否成立的最后一环。

**改了什么**
- 新增 `translate_worker.py`：`LiveTranslator` —— `submit()` 投递即返回，后台线程消费；
  - 队列 `maxsize=64`，**满了丢最旧的一条**（宁可丢一条译文，也不能堵住采集）；
  - 批量窗口：取到第一条后再等 0.25 s 凑批，最多 `chunk` 条合并成一次请求；
  - 过滤：中文不翻、`norm_key` 长度 <2 不翻、只翻"频道色"（可按 `--translate-all` 关闭）；
  - `stop()` 先排空队列再退出，不丢尾巴。
- `probe_live.py`：新增 `--translate / --engine / --translate-chunk / --translate-all / --no-translate-cache`；
  每帧把新产生的事件投递给 worker；退出时打印翻译汇总并写 `logs/live_translated_<时间>.md`。
- 新增 `run_live_translate.bat`（纯 ASCII）：双击 = `--select --min-score 0.75 --translate`。
- `translate_text.write_pairs_md()`：把"原文/译文对照表"的写入抽出来，`translate_log` 与实时通道共用。
- 两处踩坑修复见下。

**为什么**
- **必须分线程**：OCR 300~1000 ms + 翻译 300~6000 ms，串进主循环会把 2~3 fps 拖到 1 fps 以下，而且**采集会跟着停**——那就真开始漏消息了。
- **颜色比较必须按距离聚类**：同一频道色每帧抖动（`#00AFEB`/`#00A4DD`/`#00AFEA`），用精确 hex 比较会让 3/4 的聊天被当成系统提示丢掉；改用 `step=32` 量化仍不够（落在相邻桶），最终改成"到已有代表色距离 ≤40 即同色"。
- **缓存键必须带版本号**：实现了"只翻正文"之后，缓存里旧值（带 `[Ir1s]:` 前缀）被原样命中，译文里出现重复前缀。加 `CACHE_VERSION` 前缀根治——**改了送翻口径就升版本**。

**怎么验证的**
- `--engine echo` 回放：投递 11 → 已译 7、跳过中文 3/无文字 1、**非频道色 0**（颜色聚类修好后青色全中）。
- `--engine mymemory` 回放 14 s：**采集仍 3.1 fps**（与不翻译时一致）、翻译批量 4 条约 6 s、队列丢弃 0、Ctrl+C 后仍把剩余 2 条译完。详见 E10。
- `run_live_translate.bat` 纯 ASCII（非 ASCII 字节 0）+ 参数路径实测通过。

**遗留**
- 免费引擎 ≈1.5 s/条，实时体感迟钝；**换 LLM 后应降到 0.3~0.8 s**（代码只换 `--engine llm` + 三个环境变量）。
- 实时通道只在回放环境验证，真机（真实对局密度）下队列丢弃率待测。
- 译文目前只到控制台与 md 文件；**悬浮窗（产品形态）未做**，这是把"能用"变成"好用"的下一步。

## D18 · 2026-10-25 · 翻译质量抽样后的两个修正（并锁定"不为免费引擎优化"）

**目的**：看过 E9 的 20 条译文后，只修真正属于"我们代码"的问题；把"译文质量差"明确归类为**已知且可接受**，不再投入。

**改了什么**
- `translate_log.dedupe()`：增加"子串丢弃"——若某条消息的归一化键是另一条的**子串**（按长度 ≥4 判定），只保留完整版。原因：同一长句会先以 2 行版、后以 3 行版出现，两条都翻白花一次调用，报告里还会出现两条几乎相同的译文。
- 新增 `mark_untranslated()`：译文与原句相似度 ≥0.9 时，输出前加 `⟨未翻⟩`，并在统计里单独计数。原因：`lol what` / `ns gg wp` 这类被引擎**原样返回**，报告里看着"有译文"，实际是照抄——这是对质量判断的误导，必须标出来。
- `experiments.md` 新增 **E9**：免费引擎 20 条质量分层 + 失败模式归类。

**为什么**
- 这两条都是**报告诚实性**问题，不是翻译能力问题：一个让我们少花钱、一个让我们不误判。用户明确表态"黑话不认识没问题，后续换更好的翻译，本轮只探索可行性"，所以**不再为免费引擎的译法做任何优化**（此决定写入 AGENTS.md 免验证区）。

**怎么验证的**：同一份日志重跑——去重后仍 20 条但不再出现"短版+长版"成对；4 条英文短句被正确标成 `⟨未翻⟩`；缓存命中 16 条（之前翻过的复用）。

**遗留**
- 免费引擎的质量天花板已定性，后续不再评估其译法；换 LLM 后需要重新做一次质量抽样（届时才有意义）。
- 本轮唯一值得继续投入的方向是**输入侧清洗**（OCR 错字会直接毁掉整句翻译），已记在 E9 结论。

## D17 · 2026-10-25 · 新增 `run_translate.bat`（双击测试离线翻译）

**目的**：让"点两下就能看到译文"成为可能，不用记命令行、不用配 key。

**改了什么**：新增 `run_translate.bat`
- 双击 = 取 `logs/` 下最新日志 → 免费引擎（自动探测）→ 只翻前 20 条（默认 `--limit 20`，几十秒内结束）；
- 跑完**自动用默认程序打开**生成的 `logs/translated_<时间>.md`；
- 传任意参数即完全覆盖默认（`run_translate.bat --limit 36`）；
- 纯 ASCII、`chcp 65001`、venv 缺失时给明确提示（沿用其它 bat 的约定）。

**为什么**
- 双击是这台机器上最省事的入口；`--limit 20` 是为了让"试一下"的反馈时间短、免费接口不被频繁调用。
- **跑完自动打开结果文件**：否则用户还得自己去 `logs/` 里找最新的 md，体验断在最后一步。
- 用 `dir /b /o-d` 取最新的 `translated_*.md`，而不是让 Python 回传路径——bat 拿 python 的 stdout 很别扭，且不需要精确到某一次。

**怎么验证的**：`run_translate.bat --limit 4` 实测——引擎探测（google 超时 → mymemory 可用）、翻译 4 条（缓存命中 3 条，256 ms/条）、结果 md 生成、自动打开、正常退出；纯 ASCII 校验非 ASCII 字节 = 0。

**遗留**
- 目前只有"探针 / 判读 / 翻译"三个 bat，判读那步还得敲 `python analyze_log.py ...`（因为要带 `--expect` 参数）。若常用，可以再加一个 `run_analyze.bat`。

## D15 · 2026-10-25 · 接入免费翻译引擎（探索用）

**目的**：项目现阶段只用于探索，不花钱。先用免费接口把"原文→译文"这条路真正跑通并摸清质量，正式版再换 LLM。

**改了什么**
- `translate_text.py`：新增
  - `GoogleTranslator`：谷歌网页翻译非官方端点（`translate_a/single`），免 key，逐条请求 + 可配延时；
  - `MyMemoryTranslator`：MyMemory 公开免费 API，免 key，需源语言（用 `ocr_probe.guess_lang` 判定）；
  - `probe_engines()` + `engine="free"`：启动时逐个试翻一句，选第一个能用的（**不写死引擎**）。
- `translate_log.py`：`--engine` 增加 `free / google / mymemory`，默认 `free`；新增 `--delay`；**只翻正文**（昵称前缀原样保留）。
- 修三处实测暴露的毛病：冒号漏进正文（译出 `[Ir1s]：`）、用量文案把免费引擎说成 echo、缓存按引擎分文件。

**为什么**
- **必须自动探测**：国内直连 `translate.googleapis.com` 实测超时（`URLError: timed out`），写死 Google 就等于写死"跑不起来"。
- **逐条 + 延时**：两个免费接口都不支持批量；按要求加 0.2~0.3 s 间隔，避免被限流掐掉。
- **只翻正文**：昵称是名字，翻了没意义；实测把 `[Ir1s]:` 一起送进去后，译出来是 `[Ir1s] ：`（全角冒号都变了），既浪费算力又难看。
- **术语表只对 LLM 生效**：免费接口不支持自定义术语，这点必须在文档里写明，否则会以为术语表没起作用是 bug。

**怎么验证的**
- `--engine free` 探测：`google 不可用: URLError timed out` / `mymemory 可用` → 自动切到 mymemory。
- 实测 3~6 条（日志见 `logs/translated_*.md`），例如：
  `[Ir1s]: 5초만 기다려` → `[Ir1s]: 等待5秒钟`（准确）
  `[Ir1s]:이거 진짜 너무 심한데 … 매칭 좀 공정하게 해줘` → `这真的很糟糕，但是为什么我的团队不能做到这一点呢？…请让比赛变得公平一点。`（意思大体对，语气偏书面）
- 速度：含限速延时约 **1.2~1.4 s/条**，36 条约 50 s（离线场景无所谓）。

**遗留**
- **MyMemory 质量中等**：长句意译漂移、语气变书面、专有名词直译；作为"探索期能用"够了，正式版仍应换 LLM（`--engine llm` 代码已就绪）。
- 两个免费接口都是**非官方/第三方**：随时可能失效或限流，且属 ToS 灰色地带——**只能探索，不可随产品分发**。
- 碎片（如 `나려`）会被翻成 `Narrying` 这类无意义结果：垃圾进垃圾出，属预期，需要在输入侧继续过滤。
- 术语表、批量请求、token 用量统计这些只为 LLM 设计，免费引擎路径用不上。

## D14 · 2026-10-25 · T0：离线批量翻译（翻译后端抽象 + 缓存 + 术语表）

**目的**：翻译是继 OCR 之后**第二个真实不确定项**。先离线把历史日志批量翻一遍，用最小成本回答"翻译质量够不够用、一场要花多少钱"，不碰实时链路。

**改了什么**
- 新增 `translate_text.py`：翻译后端抽象——`EchoTranslator`（不联网，验证管道）、`LlmTranslator`（任何 OpenAI 兼容接口，默认 DeepSeek）、`CachedTranslator`（按 `norm_key` 缓存）；内置守望英雄名与黑话术语表；统计 token 用量。
- 新增 `translate_log.py`（T0 执行器）：读日志 → 按频道色过滤 → 去重 → 分批翻译 → 输出 Markdown 对照表 + 统计。
- `.gitignore`：新增 `cache/`（含聊天原文与译文，隐私）、`translate_config.json` / `.env`（可能含 key）。

**为什么**（每条都是设计取舍）
- **零新增依赖**：只用标准库 `urllib`。本机 `.venv\pip.exe` 已失效（见 AGENTS.md），能不装包就不装。
- **缓存键直接复用 `norm_key`**：它剥掉昵称前缀与标点，`[r1s]: gg` / `※[Ir1s]: gg` / `[r1s]:gg` 命中同一条缓存。游戏聊天重复率极高，这一步省掉大半调用。
- **只翻"频道色"的行 + 中文不翻**：E8 实测 51 条事件里 12 条是黄橙系统消息、2 条中文，过滤后 36 条 —— 省钱且避免"中文→中文"这种有害输出。
- **条数对不上就整体降级**：模型返回的数组长度与输入不一致时，整批改用原文加标记。**绝不允许按顺序硬配**——那会把 A 的译文配给 B，比不翻更糟。
- **缓存按引擎分文件**（`cache/translate_<engine>.json`）：踩过——先用 echo 跑通时写进去的假译文，切到 llm 后会被当真译文命中。
- **收尾必须显式 `save()`**：踩过——只在攒满 `save_every` 条时落盘，最后一批（36 条里的 12 条）会丢。

**怎么验证的**
- `--engine echo` 全链路跑通：51 事件 → 过滤 12 非频道色 + 1 无文字 + 2 中文 → 36 条候选 → 去重 36 → 生成 Markdown 对照表。
- 缓存两轮实测：第一轮命中 0、第二轮 **命中 36/36**，缓存文件按引擎隔离。
- 未设 key 时 `--engine llm` 给出明确提示而不是崩栈。

**遗留**
- **真 LLM 调用尚未验证**（缺 API key）：质量、延迟、失败率都还是纸面设计。下一步就是设 key 跑 `--limit 20`。
- 术语表是凭经验写的默认值，需要用真机高频句校对（尤其英雄名国服译名）。
- 单价未配置（`PRICE_*` 都是 0），只报 token 数不估金额——不猜官网价格。
- T1（实时管道：队列 + 翻译线程）未做；T0 结论出来后再决定是否值得做。

## D13 · 2026-10-25 · 残片照常翻译 + 补全更新机制（修正 D12 的思路）

**目的**：用户指出 D12 的"抑制残片"不完整——如果**先**滚到消息下半部（头部从未出现在画面里），子串抑制根本挡不住；而且残片本身是有翻译价值的，正确的做法不是丢，而是**先翻出来、等完整版出现再更新文本**。

**改了什么**
- `probe_live.emit()`：新增"补全更新"识别——若新候选的 key **包含**某条已报消息的 key（旧的是新的子串），判定为同一条消息这次读得更全 → 打印时标 `↻`、事件里写 `"updates": <old_key>`、从历史中移除旧 key、**不计入新行**而计入 `补全更新` 次数。
- 事件新增 `"partial": true/false`（无昵称前缀 = 可能是残片或系统消息），打印时标 `…`。
- `Stats` 新增 `updated`，汇总与 JSON 都输出；`analyze_log` 时间线显示 `↻` / `…` 标记并单列"补全更新"段。
- `drop_clipped` 的阈值改为可配：`--min-height-ratio`（默认 0.7），并**明确语义**——框太矮（只露一条缝）= **没有翻译价值**，直接丢；框高正常但缺前缀 = 残片，保留翻译。
- 修了一个接线 bug：`--min-height-ratio` 之前只加到了 argparse，`ensemble()` 调用处没传，导致改参数无效（实测 0.7 与 0.01 输出完全相同才发现）。

**为什么**
- 用户的原话是权衡的关键：残片翻出来"貌似也没问题"，代价只是"完整版出现后要更新"。相比丢弃，这条路既不会漏信息，也不需要赌"完整版一定先出现"。
- 两种"缺头"必须分开处理：**裁太狠**（框高 <70% 中位数）连字都只剩半截，翻了也是错 → 丢；**框正常但无前缀**（头部滚出去了）文字完整可读 → 翻，并标 partial。
- `updates` 用归一化 key 的子串关系判断，能穿透前后缀抖动；要求双方 key 长度 ≥4，避免 `gg` 这类短词误判。

**怎么验证的**
- 离线把新逻辑套到 E8 的真机日志：51 条 → **新消息 44 / 补全更新 5 / 残片抑制 2**。其中两处正是用户描述的场景：
  `可发送至该频道的信息数量有限。请稍后再` 替换先前报的 `的信息数量有限。请稍后再`；
  `[Ir1s]:이거 진짜 너무 심한데 … 공정하게 해줘` 替换先前的 2 行版本。
- `--min-height-ratio` 实测生效：裁切样本在 0.7 下丢掉 h=7 与 h=16 两行，改 0.3 后被裁行（0.736）重新出现。
- 四个样本截图回归正常；探针冒烟输出含"补全更新 0 次"（静态回放无更新，符合预期）。

**遗留**
- 补全更新目前只**标记**在事件里，还没有真正"替换已显示条目"的能力——那属于产品层（UI 需要能更新列表项），等做悬浮窗时实现。
- 若"补全"实际是两条不同消息被横向合并成一条（`our tank is throwing…` + `heal me mercy pls`），也会被判成更新——语义上不准确，但不会丢内容。等真机再观察频率。
- `min-height-ratio=0.7` 是经验值，换游戏/分辨率要复测。

## D12 · 2026-10-25 · 抑制"头部被裁掉的残片"

**目的**：用户现场发现——长句被游戏拆成多行后，**头部滚出视口**，屏幕上只剩无昵称前缀的续行，会被当成一条新消息报出（数字层面看是"没昵称前缀的部分行"）。

**改了什么**：`probe_live.emit()` 增加 `history`（最近 40 条已报消息的 `(key, text)`）与 `prefix_re`，新增一条判定：
> 当前行**没有昵称前缀** 且 `len(key) >= 4` 且 `key` 是某条**已报**消息 `key` 的子串 → 判定为残片，不报。

**为什么**
- 不能只看"有没有昵称前缀"就丢：**系统提示也没有前缀**（如「可发送至该频道…」），会被误杀。加上"必须是已报消息的子串"这个条件后，才既准确又安全。
- 用 `norm_key` 之后的形式做子串判断，可以穿透前后缀抖动与标点差异。
- `len(key) >= 4` 是防止短词误伤（`gg`、`A`、`中` 这类可能恰好出现在别的消息里）。

**怎么验证的**
- `shots/chat_team_orphan.png`（用户截图：只剩两行无前缀续行）：两行正确合并成一条 `못하지 다음 게임은 좀 잘하고 싶다 제발 매칭 좀 공정하게 해줘`。
- 把规则离线套到 E8 的真机日志上：**51 条 → 49 条**，被压掉的 2 条全部是那条长句的残片（`못하지 다음 게임은…`、`공정하게 해줘`），**零误杀**。

**遗留**
- 只能挡住"完整版先出现、残片后出现"的情况。若残片**先**出现（例如会话一开始就已经滚到一半），规则无能为力——E8 里 `言息数量有限。请稍后再`（0.6 s）就早于完整版（2.8 s）。
- 真正优雅的解法是"后来拿到完整版时回填/替换已显示的条目"，那需要产品层（UI 能更新已有条目）才做得了，等做悬浮窗时再说。

## D11 · 2026-10-25 · 自动丢弃被视口裁掉的半行

**目的**：聊天面板的滚动区会把首行/末行裁成半行（实测截图顶部只剩 `试。`、底部只剩半句），这种行必然读成乱码，并污染统计与后续合并。

**改了什么**：`explore/ocr/ocr_simple.py` 新增 `drop_clipped(entries, ratio=0.7, min_entries=4)`，在 `ensemble()` 里**先于横向/纵向合并**执行——按框高丢弃低于中位数 70% 的行。

**为什么**
- 判据只能用框高，不能用宽度：像 `试。` 这种**完整但很短**的行宽度也小、高度却正常（20px），按宽度会误杀。

- **丢弃不丢信息**：半行在随后一两帧一定会以完整形式出现（滚动方向决定），最终照样能被识别到。
- `min_entries=4` 是保护：行数太少时中位数本身不可靠，宁可不裁。

**怎么验证的**：四个样本回归——`chat_team_cut`（专门拍裁切场景）里顶部 `-LO`(h=7) 与底部 `1. π`(h=16) 消失；`chat_team_system` / `chat_team_wrapped` / 原样本**零变化**（说明没有误杀）；探针回放同样正常。

**遗留**
- `试。` 这类"续行的后半截"高度是正常的（20px），高度判据抓不到——它来自"首行已滚出视口"的换行消息。危害低（只会被当成一条很短的独立消息）。
- `ratio=0.7` 是按本机字号拍的；换游戏/改分辨率要复测。

## D6 · 2026-10-25 · 检测框按行合并（长句不再被切碎）

**目的**：修 E5 遗留的第一条——一条长聊天行被检测模型切成多段，各自成了独立消息，翻译会被拆碎。

**改了什么**

- 合并规则：**中心线高度差 ≤ 半个行高** + 水平间距在行高的 `[-0.5, 0.8]` 倍内 → 同一条视觉行；用**收敛式**（反复扫到不再变化）合并；组内按 x 排序、以空格拼接，置信度取**最大**；组内有效字符 ≤1 的段丢弃。
- `probe_live.py`：同步传 `merge`，事件里新增 `y`/`x` 行位字段（便于判读"是否被合并成一行"）。

**为什么**（每条都是踩过才知道的）
- 用"垂直重叠 ≥50%"判同行会**误合相邻两行**：检测框普遍带上下留白，行距小时两框能重叠 40%（本项目实测把 `[队伍]` 与下一条合成一行）。
- 合并必须**收敛**：按 (top,left) 贪心一遍时，第 3 段因为第 1 段先吸收了第 2 段才变"相邻"，单趟会漏合（实测 3 段只合了 2 段）。
- 单字符段要丢：真实截图里左侧头像区被误检成 `や`，几何上确实与聊天行同行同高，拼进去就污染原文。
- 置信度取 max 而不是 min：前缀碎片分数低但不影响正文可信度，取 min 会把整行误标成低质量。

**怎么验证的**：5 个几何用例全部符合预期（3 段合 1 且拼出的句子与原句逐字一致；相邻两行不合；**行距很小、框带 40% 留白的两行也不合**；昵称前缀与正文合 1；水平间距过大的不合）。真实截图 8 行 → 6 行（`や` 被丢、日文行完整、`[队伍] 按下TAB切换频道` 合一）。探针回放同场景"累计行"从 56 降到 30。

- `gap_ratio=0.8`、中心线半个行高这两个阈值是拍的，需要真机滚动数据校准（滚动时行在天上飞，几何抖动更大）。
- 合并用单空格连接，中文行可能出现多余空格（对翻译影响小，但影响"原文回显"的美观）。
- 尚未在真机上验证合并效果，等 E6（滚动测试）数据。

- 新增 `chat_text.py`：`norm_key()` —— 剥掉行首 `[昵称]:` 前缀（全/半角冒号都认），只保留字母数字（中文/韩日文在 Python 里都是 alnum，一次剥掉空白、标点、`※·▲[]`），再把整句重复片段折叠（`5초만기다려×3` → ×1）。
- `probe_live.py`：去重状态从"原文集合"改为两个以 `norm_key` 为键的字典——`seen`（最后一次在屏幕上看到的时刻，`--visible-ttl` 默认 6 s 内视为"还在屏幕上"，挡住漏读一帧的误报）与 `reported`（最后报出时刻，`--recent-ttl` 默认 120 s 内不重报）。
- `analyze_log.py`：新增「按正文归一化后的真实消息」段（把抖动变体收回一组，用最高分那条代表）、「OCR 产出率」段、以及 `--expect chat_samples.txt` 召回核对（拿测试句当标准答案，逐句标 ✓/~/✗）。

**为什么**
- 真机数据里同一句的原文变体是 `[r1s]:메르시 힐 좀 줘 제발` / `※[Ir1s]:메르시 힐 좀 줘 제발` / `S]:메르시힐좀 줘 제발`…… **正文一字不差，抖的只有前缀**。用原文字符串做去重键，等于每帧都判成新消息。
- 之前"上一帧可见集合"的写法还有个隐含要求：任一帧漏读该行，它就从集合里消失，下一帧又算新消息。改成"带存活窗口的 last_seen"才稳。
- `--expect` 是补上"没有标准答案就只能是猜"这个短板：有测试句文件就能直接算召回，不必靠空窗间隔去推。

**怎么验证的**：同一份真机日志离线重放（288 条事件）：归一化后不同 key 从 92 降到 89（折叠重复片段生效）；加 120 s 抑制后剩约 100 条，而这只是上限——真实运行时"消息还在屏幕上"期间根本不会重报。`norm_key` 另做了样例单测（前缀变体全部归一到同一 key）；回放冒烟确认新逻辑不误杀真实新行。

**遗留**
- 归一化去重只能压"同一句的变体"，压不掉**误读成别的字**的碎片（如 `뜻이서니음개금`），那要靠提高 `--min-score` 或"连续两帧一致才采信"。
- 长句会被检测框切成多段（实测一条长韩文句被切成 3 段、各自成为独立 key），翻译前需要按行位合并相邻框。
- `--visible-ttl` 6 s、`--recent-ttl` 120 s 是拍的，等下一轮真机数据校准。

**为什么**

**遗留**
- `logs/` 会持续累积，没有清理策略（暂按手动删；长期跑要加保留最近 N 份）。
- 判读脚本的相似度阈值（0.80）与低质量阈值（0.6）都是拍的，等真机数据再校准。

## D3 · 2026-10-25 · 半实时探针：改成长期运行 + 日志瘦身

**目的**：让探针能在真实游戏里挂半小时以上，同时不把屏幕刷满。

**改了什么**（全部在 `probe_live.py`）
- `--duration` 默认 `0` = 一直跑，Ctrl+C / 关窗口结束；中断后照常打印稳态汇总。
- 日志只输出**新出现的行**，重复行一个字不打；状态改由 `--heartbeat` 心跳行呈现（默认 10 秒一行）。
- 去重改为两级：`visible`（上一帧可见集合，老消息不重报）+ `recent`（TTL 内已报集合，默认 120 秒）。
- 新增 `--dedupe-similar`（默认 0=关）：同一行位相似度达阈值即判为识别抖动，不报。
- `stdout` 加 `line_buffering=True`：输出重定向到文件时不再块缓冲，长跑也能实时看。

**为什么**
- 旧版每次 OCR 都把整屏 8 行全打一遍，其中 6~7 行是没变的老消息，长跑时日志量是有效信息的 4 倍以上。
- 去重必须跟"聊天的语义"走：一行文字是**待在那儿**的，所以拿"上一帧可见集合"比"全局历史集合"准——
  全局集合会让十分钟后又有人说的 `gg` 被永久吞掉。
- `--dedupe-similar` 默认关闭是刻意的：它可能把 `heal me` → `heal me pls` 这种真实微调也吞掉，
  该不该开要真机数据说话（见 E3）。

**怎么验证的**：`--replay shots\Overwatch_q88jLuAM85.png --sim-change-every 6 --heartbeat 3`，
后台跑 20 秒，确认无限模式、心跳、只报新行都生效（数据见 E3）；同一命令加/不加 `--dedupe-similar 0.85` 各跑 8 秒对比新行数（17 → 15）。

**遗留**
- 串行循环的漏行问题**没解决**（见 D2 遗留），采集与 OCR 尚未解耦。
- `--dedupe-similar` 的合理阈值未定，等真机数据。

## D2 · 2026-10-25 · 新增 `probe_live.py`：半实时探针

**目的**：从"单帧能认出字"跨到"连续运行时站不站得住"。这是探针到工具的分界线。

**改了什么**
- 新增 `probe_live.py`：定时截屏 → 帧差 → **只在画面变化时**跑集成 OCR → 只报新行 + 稳态统计。
- 新增 `run_live.bat`（纯 ASCII 启动器，无参数时进 `--select` 框选模式）。
- 复用而非重写：框选/DPI 来自 `ocr_probe.py`，引擎与集成来自 `explore/ocr/ocr_simple.py`（`importlib` 按路径加载）。

**为什么**
- 帧差是省算力的关键：截屏 + 帧差合计 ~1.5 ms，而一次集成 OCR 是 500~1000 ms，
  静帧时跳过 OCR 等于白得 2/3 的算力（实测跳过率 50%~70%，见 E3）。
- 复用而非重写：`ocr_probe.py` 的框选已经处理了 DPI 虚拟化与多显示器负坐标两个坑，
  `ocr_simple.py` 的集成已经处理了模型配对与框对齐。重写一遍只会重踩。
- 依赖 `explore/` 下的脚本是笔临时债：它是探索产物，等确认长期要用，应上提为根目录模块。

**怎么验证的**：`--replay` 静态图 + `--sim-change-every` 人为造变化，无界面自测；`py_compile` 过；数据见 E3。

**遗留**
- **串行阻塞会漏行**：OCR 占 300~1000 ms，其间采集被堵住，聊天滚动的那几帧直接丢（不是"慢"，是"漏"）。
  下一步应解耦：采集+帧差走 30 fps 轻循环，只把变化帧丢进队列，OCR 单独线程消费。
- 局部遮挡/滚动中途截图会把同一行读成不同文本，产生**假新行**（自测 17 条 vs 实际 8 条）。
- 检测框坐标只在两模型间一致；跨帧没有做跟踪，所以"同一行"目前靠行位近似（round(top/8)）。
