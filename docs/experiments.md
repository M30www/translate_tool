## E9 · 免费翻译引擎质量抽样（MyMemory，20 条）

**条件**：用 E8 的日志（`logs/live_20261025_143827.json`）离线翻译，引擎 `free` → 自动选中 `mymemory`
（google 直连超时）。逐条人工判读质量。结果文件 `logs/translated_20261025_150124.md`。

**命令**
```
run_translate.bat                 （= translate_log.py --limit 20，免费引擎）
```

**结果：20 条的质量分层**

| 表现 | 条数 | 例子 |
|---|---|---|
| ✅ 意思正确/可读 | 7 | `5초만 기다려`→等待5秒钟；`全然問題ない`→完全没有问题；`あと10秒で終わる`→10秒后结束 |
| 🟠 意思偏但不算错 | 3 | `매칭 좀 공정하게 해줘`→请让匹配变得公平一点；`heal 20%남았다`→剩余治疗20% |
| ❌ 游戏术语/黑话崩 | 5 | `ult ready in 20s`→**20秒内超级就绪**（ult=大招）；`our tank is throwing`→**我们的坦克正在投掷**（throwing=送）；`マーシー回復`→**Marcy，请康复**（=天使，回复=治疗）；`草もう無理`→**再也不能吃草了**（草=日文网络梗"笑"） |
| ❌ 整句未翻译（原样返回） | 4 | `lol what`、`ns gg wp`、`diff genji`、`heal me mercy pls` |
| 🗑 输入本身是垃圾 | 3 | `나려`→Narrying；`5소만 기나러`→5Sawman Ginarae（OCR 碎片） |

**结论**
- **可行性结论（本轮唯一要回答的问题）：通过。** 链路 `OCR → 过滤 → 只翻正文 → 缓存 → 输出对照表` 端到端跑通，
  20 条约 25 s（1.2 s/条，含防限流延时）；引擎可通过 `--engine` 一行切换、无需改代码。
- **译文质量不达标属预期，不作为本轮判据**：黑话/英雄名不认识、英文短句原样返回，都是免费接口的能力边界。
  **后续换 LLM 即可，不必为免费引擎优化译法。**
- 质量问题里唯一值得现在就管的是**输入侧**：OCR 错字会直接毁掉整句（`이거 신싸 너무 심안네…` → "这是如此闪亮我的轮辋…"），
  所以继续投入应该放在清洗与行重组上，而不是翻译侧。
- **残片如实翻这一点成立**：`이거 진짜 너무 심한데 우리 팀 왜 이렇게`（被裁断的残片）译成"这真的太严重了，但是为什么我的团队如此"——**停在原文该停的地方，没有脑补**。这条对将来的 LLM 同样适用。
- 免费接口**不支持术语表**，英雄名/黑话在当前引擎上无解，也不再尝试解。

**注意事项**
- 本轮同时验证了两个代码改进：① 离线去重增加"子串丢弃"，同一长句的 2 行版与 3 行版只翻一次；② 译文与原句相似度 ≥0.9 时标 `⟨未翻⟩`，避免"看起来有译文其实是照抄"的误导（本轮标出 4 条）。
- 免费引擎**只能验证管道，不能作为质量基线**。要判断"这工具能不能用"，必须换 LLM（代码已就绪，只换 `--engine llm` 与三个环境变量）。
- 换算成本：20 条约 25 s（1.2 s/条，含防限流延时），免费接口无 token 计量。

## E8 · 真机第四测（--min-score 0.75 + 半行丢弃上线后）

**条件**：78.91 s / 229 帧；区域正常；用户逐条发送 + 滚动。日志 `logs/live_20261025_143827.{log,json}`。
启动参数为 `run_live.bat` 里写死的默认值（`--select --min-score 0.75`）。

**命令**
```
run_live.bat（双击，默认 --select --min-score 0.75 → Ctrl+C）
python analyze_log.py logs\live_20261025_143827.json --expect chat_samples.txt
```

**结果**

| 指标 | 本轮 | E7（上一轮） |
|---|---|---|
| 跳过率 / OCR 次数 | 68.1% / 73 次 | 79.7% / 46 次 |
| 单次 OCR p50 / p95 | 487.6 / 637.0 ms | 529.6 / 764.1 ms |
| 端到端 p50 / p95 | **547.3 / 692.6 ms** | 589.7 / 837.4 ms |
| 新行 / 归一化后唯一 | 51 / 51（重复 0） | 55 / 55 |
| **低质量行** | **1 条（只有 `中`）** | 8 条 |
| 召回 | 25 全对 | 25 全对 |
| 文字颜色类数 | 5 类（青 39 / 橙 5 / 亮黄 5 / 灰蓝 1 / 白 1） | 5 类 |

**结论**
- **`--min-score 0.75` + 半行丢弃（D11）组合非常有效**：低质量行从 8 条降到 1 条，且召回没有任何损失（仍 25/25）。E7 里那一堆 `y≈101` / `y≈358` 的误读碎片全部消失。端到端 p95 也顺带降到 693 ms。
- **仍然存在的问题（用户现场发现）**：长句被拆行后，**头部滚出视口**，屏幕只剩无前缀的续行，会被当成一条独立消息报出。典型证据：
  - `[51.5s] 못하지 다음 게임은 좀 잘하고 싶다 제발 매칭 좀 공정하게 해줘`（无前缀）
  - 而完整版 `[6.5s] [Ir1s]:이거 진짜 너무 심한데 … 공정하게 해줘` 早已报过
  → 已在 D12 用"残片抑制"处理（离线复算：51 → 49，压掉的 2 条全部是这条长句的残片，零误杀）。
- 另有 6 簇"假新行"，成因是**增量识别**：同一条长消息先是读到 2 行、下一帧读到 3 行，文本不同 → norm_key 不同 → 报两次。属可接受的冗余（后者更完整）。

**注意事项**
- 本轮跳过率降到 68%（前几轮 80%），因为用户一直在滚动，画面持续变化 → 触发更多 OCR。属预期。
- `言息数量有限。请稍后再`、`的信息数量有限。请稍后再` 这两条残片出现在 0.6 s / 2.2 s，**早于**完整版（2.8 s），所以"子串抑制"挡不住——它只能挡住"完整版先出现"的情况。

## E7 · 真机第三测（颜色 + 同色续行上线后的首跑）

**条件**：71.76 s / 227 帧；区域正常框住聊天面板；用户逐条发送 + 上下滚动聊天记录。
日志 `logs/live_20261025_142731.{log,json}`。机器重载档（DSH/Steam/QQ 运行中，见 E4）。

**命令**
```
run_live.bat（框选聊天面板 → 发送/滚动 → Ctrl+C）
python analyze_log.py logs\live_20261025_142731.json --expect chat_samples.txt
```

**结果**

| 指标 | 数值 | 与 E5 对比 |
|---|---|---|
| 跳过率 / OCR 次数 | 79.7% / 46 次 | 相近 |
| 单次 OCR p50 / p95 | 529.6 / 764.1 ms | 相近 |
| 端到端 p50 / p95 | 589.7 / 837.4 ms | 相近 |
| 新行 / 归一化后唯一 | **55 / 55（重复 0 条）** | E5 是 288 / 98 |
| 召回（对照 chat_samples） | **25 条完全正确、0 条缺失或部分** | E5 是 24 完整 + 1 部分 |
| 文字颜色类数（聚类后） | **5 类**：青 ×43、亮黄 ×6、橙 ×4、灰蓝 ×1、白 ×1 | — |

**结论**
- **D9 的同色续行合并真机验证通过**：长句 `이거 진짜 너무 심한데 우리 팀 왜 이렇게 못하지 다음 게임은 좀 잘하고 싶다 제발 매칭 좀 공정하게 해줘` 完整召回（E5 里它被切成 3 段）。这是本轮最大变化。
- **颜色语义得到量产数据确认**：43 条青色全部是聊天、6 条亮黄全是好友动态、4 条橙全是限流警告、灰蓝是 UI 提示、白是输入法状态。**零混色**，说明按颜色过滤消息类型这条路可行。
- 重复报彻底消失（55 新行 = 55 唯一），D5 的归一化去重稳定工作。

**本轮暴露的两个新问题**
- **区域上下边缘各有一行被裁切 → 每次滚动都产生误读碎片**：低置信度误读（0.53~0.72）集中在 `y≈101~106`（顶部第一行）与 `y≈358~366`（底部行），例如 `[1희· 3소만 기니너`、`[" 1ə]· n`、`F`、`「r11.注大t打野别￥了`。真实消息的置信度普遍 ≥0.88，所以这类碎片可以用置信度门槛砍掉大半。
- **`y≈316~317` 那一行反复出现两条消息被拼在一起**（`[Ir1s]:노 리미트 디바 이상함 다lr1cl·5초마 기다려`、`[Ir1s]:5초만 기다려5초만 기다려5초만 기다려 [lr1cl·5초만 기다려`）。这一行在多个不同时刻都出现，怀疑是聊天面板底部的重叠/重影渲染区（或输入框上方的残留行），需人工对照屏幕确认。

**注意事项**：本次仍是"手动发送 + 手动滚动"，节奏远慢于真实对局；结论里的延迟数字不代表高强度刷屏场景。

**条件**：88.02 s / 283 帧；框选区域 `934 x 506 @ (85,604)` —— **框到了桌面/开始菜单和终端窗口本身**，
不是游戏聊天区。日志 `logs/live_20261025_141257.{log,json}`。

```
python analyze_log.py logs\live_20261025_141257.json --expect chat_samples.txt
```

**结果**

| 指标 | 数值 |
|---|---|
| 跳过率 / OCR 次数 | 77.7% / 63 次 |
| 单次 OCR p50 / p95 | 438 / 704 ms |
| 新行 / 归一化后不同消息 | **106 / 106（重复 0 条）** |

**结论**
- **D5 的归一化去重确实生效**：对比 E5 的 288 条新行 / 98 条唯一（重复率 66%），本次 106 条新行 / 106 条唯一，**重复 0 条**。虽场景不同（桌面滚动），但同一句多帧重复报的问题已经不再出现。
- **暴露"自喂循环"风险**：区域内含终端窗口时，探针会 OCR 到自己打印的心跳行（日志里出现 `27 2.7fps | 跳过 55.6% | 0CR 12 次…`）。将来做了悬浮窗更要把自己的窗排除在采集区外。

**注意事项**：本次数据**不能**用于评估聊天识别质量或漏行率。它是一次事故记录，价值在两处——去重策略得到验证、自喂循环被提前发现。

## E5 · 真机首测（守望先锋实战 271 秒）

**条件**：`run_live.bat` 框选聊天区，用户手动逐条发送 `chat_samples.txt` 里的句子（约 25 条），
期间游戏全屏窗口化运行。日志 `logs/live_20261025_135316.{log,json}`。机器同时开着 DSH/Steam/QQ（重载档，见 E4）。

**命令**
```
run_live.bat                                        （框选 → 一直跑 → Ctrl+C）
python analyze_log.py logs\live_20261025_135316.json --expect chat_samples.txt
```

**结果**

| 指标 | 数值 |
|---|---|
| 运行 / 帧数 | 271.35 s / 886 帧（3.27 fps） |
| 帧差跳过率 | **81.9%**（160 次触发 OCR） |
| 单次 OCR | p50 529 ms / p95 685 ms |
| 端到端 | p50 586 ms / p95 741 ms |
| 累计识别行 / 报出的"新行" | 1258 行 / **288 条** |
| 归一化后不同消息（含噪声） | 89 条 |
| 真实测试句召回 | **24 句完全正确 + 1 句部分**（长句被切碎） |
| OCR 产出率 | 118/160 次触发生成了新行（74%） |

**结论**
- **精度够用**：韩文（ko5）、中文/日文/英文（v6）逐条测试句的召回 24/25，置信度多在 0.87~1.00。
- **漏消息不是当前主要矛盾**：手动逐条发送时，"疑似漏行空窗"的 29 处大多是没发消息的空档，没有整条丢失。此前担心的串行阻塞漏行，在 1~2 秒一条的节奏下没有暴露。
- **重复报是主要矛盾**：288 条新行里真实消息约 25 条，一条最多被报 22 次。根因是行首昵称前缀抖动（`[r1s]:` / `※[Ir1s]:` / `S]:`），而旧去重键用的是原文字符串。
- **长句会被切碎**：一条长韩文句被检测框分成 3 段（`이거진짜너무심한데...` / `못하지다음게임은...` / `공정하게해줘`），召回核对里表现为"部分识别 0.63"。
- **框选区域混入非聊天内容**：战网好友提示（`2位好友正在玩《守望先锋》`）、频道提示（`[队伍]`、`按下TAB切换频道`）、纯符号行都会进 OCR。

**注意事项**
- 游戏有发送限流：连发时出现 `可发送至该频道的信息数量有限请稍后再试`，喂测试句的节奏要放慢到 ≥2 秒，否则部分句子根本没发出去，会被误算成"漏识别"。
- 本次数据在"重载 + 游戏运行"下取得，耗时数字比 E3 的回放结果更接近真实体感，但仍受当场负载影响（参考 E4）。

**废弃提示**：本次数据的"288 条新行"基于 D5 之前的旧去重逻辑；D5 之后预期会显著下降，需要重测并新增一条 E6。

## E1 · OCR 路线对比（同一张真实截图）

**条件**：`shots/Overwatch_q88jLuAM85.png`，737×421，守望聊天区，含中文/日文/韩文/英文混排，共 8 行文字。
机器空闲（仅有系统常驻进程）。

**命令**
```
python ocr_probe.py --image shots\Overwatch_q88jLuAM85.png --lang ko
python ocr_probe.py --image shots\Overwatch_q88jLuAM85.png --lang ko --rec-model ko5 --det-limit 320 --no-cls --repeat 3
python explore\ocr\ocr_simple.py shots\Overwatch_q88jLuAM85.png
```

**结果**

| 配置 | 识别情况 | 单次耗时 |
|---|---|---|
| probe 默认：ko4 + det 736 + 开 cls | 5 行中仅 2 行含韩文，其余乱码（如「不在脫天我道配史」），平均置信度 0.683 | 618 ms（推理 572） |
| 单头 ko5 + det 320 + 关 cls | 只韩文那行正确，其余退化成 `[re]:`、`[]`、`TAB` | **194 ms**（推理 157） |
| 双头集成 ko5 + v6（ocr_simple） | **8 行全对**，置信度 0.837~1.000 | **515 ms** |

**结论**
- 单一韩文模型不是"识别不准"，而是**字典所限根本吐不出别的文字**；多语种混排必须双头逐框择优。
- 择优判据用"结果里有没有谚文"，不能用置信度：日文模型读简体中文会给 0.972 的高分错字。
- 集成方案代价是可接受的（515 ms 级别），换来的是全覆盖。

**注意事项**
- probe 输出的「目标语种命中率」在多语种图上是误导性指标，别据此判断可行性。
- 之后复测同一命令得到 ~1000 ms，差别来自机器负载（E4），不是代码改动。

## E3 · 半实时链路稳态（回放模式）

**条件**：静态图回放 + 人为造变化（`--sim-change-every`），无界面自测。
负载状态分两档：**轻载**（仅本进程）与**重载**（同时跑着 DSH Desktop / Steam / QQ 等）。

**命令**
```
python probe_live.py --replay shots\Overwatch_q88jLuAM85.png --sim-change-every 4 --heartbeat 4 --duration 9
python probe_live.py --replay shots\Overwatch_q88jLuAM85.png --sim-change-every 4 --duration 8 --dedupe-similar 0.85
```

**结果**

| 指标 | 轻载 | 重载 |
|---|---|---|
| 截屏（回放取帧） | 0.3~0.5 ms | 0.3~0.5 ms |
| 帧差 | 0.8~1.0 ms | 1.0~1.4 ms |
| 集成 OCR 单次 | 287~537 ms | 690~1254 ms |
| 跳过率 | 50% | 63%~70% |
| 实际循环 | 3.1 fps | 2.0~2.5 fps |

假新行（造变化遮住半行日文、导致同一行被读成 `段プレイしないなら` / `イしないなら` / `：こないなら` 等变体）：
不开抖动抑制 **17 条**新行（实际只有 8 条）→ `--dedupe-similar 0.85` 后 **15 条**。

**结论**
- 帧差这个闸门是划算的：~1.5 ms 的判断省掉 2/3~70% 的 OCR。
- 循环被 OCR 串行阻塞，实际只有 2~3 fps（目标是 4 fps），聊天滚动期间会漏帧。
- 近似去重能压掉一部分抖动噪声，但压不干净：同一行被遮挡一半时，输出与原文差异远超 15%。

**注意事项**：回放模式的"截屏"只是内存拷图，真实屏幕采集要慢得多（GDI/ImageGrab 抓窗口预计 10~30 ms），
所以**本表的截屏耗时不能代表真机**；真机数据要重测并新增 E5 之类的条目。

## E4 · 机器负载对 OCR 耗时的影响（元实验）

**条件**：同一脚本、同一张图、同一套模型，仅改变机器上是否有其它重负载进程。

**命令**
```
python explore\ocr\ocr_simple.py shots\Overwatch_q88jLuAM85.png      （连跑 3 次）
```

**结果**：空闲时 515 ms；机器上跑着 DSH Desktop（CPU 累计 300 s+）、steamwebhelper、QQ 时 966~1109 ms。

**结论**：**同一份代码的耗时能差 2 倍**。所以：
- 引用任何耗时数字都必须当场复测，不能拿历史数字当基准；
- 判断"够不够快"要看相对指标（跳过率、新行数是否对得上），别盯绝对毫秒；
- 真机测试时游戏本身会占 CPU/GPU，实测可能比我这边更慢，预算要留余量。

**注意事项**：这也是为什么本项目所有性能结论都标注了负载状态。
