## E6 · 真机第二测（区域框错 + 自喂循环事故）

**条件**：88.02 s / 283 帧；框选区域 `934 x 506 @ (85,604)` —— **框到了桌面/开始菜单和终端窗口本身**，
不是游戏聊天区。日志 `logs/live_20261025_141257.{log,json}`。

**命令**
```
run_live.bat（框选后直接 Ctrl+C 结束）
python analyze_log.py logs\live_20261025_141257.json --expect chat_samples.txt
```

**结果**

| 指标 | 数值 |
|---|---|
| 跳过率 / OCR 次数 | 77.7% / 63 次 |
| 单次 OCR p50 / p95 | 438 / 704 ms |
| 新行 / 归一化后不同消息 | **106 / 106（重复 0 条）** |
| OCR 产出率 | 33/63（52%） |
| 召回（对照 chat_samples） | 24 完全正确 + 1 部分（长句仍分 3 段） |

**结论**
- **D5 的归一化去重确实生效**：对比 E5 的 288 条新行 / 98 条唯一（重复率 66%），本次 106 条新行 / 106 条唯一，**重复 0 条**。虽场景不同（桌面滚动），但同一句多帧重复报的问题已经不再出现。
- **暴露"自喂循环"风险**：区域内含终端窗口时，探针会 OCR 到自己打印的心跳行（日志里出现 `27 2.7fps | 跳过 55.6% | 0CR 12 次…`）。将来做了悬浮窗更要把自己的窗排除在采集区外。
- **长句分段的真因不是检测框切碎，而是游戏自己换行**：同一次 OCR 触发内出现 y 相差 25px（正好一行高）的独立框 → D6 的横向合并无效，需要纵向的续行合并（见 D8/D9）。
- 区域必须只框聊天列表；本次抓到的全是 Windows 开始菜单、Edge、Krita、UU 加速器之类。

**注意事项**：本次数据**不能**用于评估聊天识别质量或漏行率。它是一次事故记录，价值在两处——去重策略得到验证、自喂循环被提前发现。

## E5 · 真机首测（守望先锋实战 271 秒）

**条件**：`run_live.bat` 框选聊天区，用户手动逐条发送 `chat_samples.txt` 里的句子（约 25 条），
期间游戏全屏窗口化运行。日志 `logs/live_20261025_135316.{log,json}`。机器同时开着 DSH/Steam/QQ（重载档，见 E4）。

**命令**
```
run_live.bat                                        （框选 → 一直跑 → Ctrl+C）
python analyze_log.py logs\live_20261025_135316.json --expect chat_samples.txt
```

**结果**

| 指标 | 数值 |
|---|---|
| 运行 / 帧数 | 271.35 s / 886 帧（3.27 fps） |
| 帧差跳过率 | **81.9%**（160 次触发 OCR） |
| 单次 OCR | p50 529 ms / p95 685 ms |
| 端到端 | p50 586 ms / p95 741 ms |
| 累计识别行 / 报出的"新行" | 1258 行 / **288 条** |
| 归一化后不同消息（含噪声） | 89 条 |
| 真实测试句召回 | **24 句完全正确 + 1 句部分**（长句被切碎） |
| OCR 产出率 | 118/160 次触发生成了新行（74%） |

**结论**
- **精度够用**：韩文（ko5）、中文/日文/英文（v6）逐条测试句的召回 24/25，置信度多在 0.87~1.00。
- **漏消息不是当前主要矛盾**：手动逐条发送时，"疑似漏行空窗"的 29 处大多是没发消息的空档，没有整条丢失。此前担心的串行阻塞漏行，在 1~2 秒一条的节奏下没有暴露。
- **重复报是主要矛盾**：288 条新行里真实消息约 25 条，一条最多被报 22 次。根因是行首昵称前缀抖动（`[r1s]:` / `※[Ir1s]:` / `S]:`），而旧去重键用的是原文字符串。
- **长句会被切碎**：一条长韩文句被检测框分成 3 段（`이거진짜너무심한데...` / `못하지다음게임은...` / `공정하게해줘`），召回核对里表现为"部分识别 0.63"。
- **框选区域混入非聊天内容**：战网好友提示（`2位好友正在玩《守望先锋》`）、频道提示（`[队伍]`、`按下TAB切换频道`）、纯符号行都会进 OCR。

**注意事项**
- 游戏有发送限流：连发时出现 `可发送至该频道的信息数量有限请稍后再试`，喂测试句的节奏要放慢到 ≥2 秒，否则部分句子根本没发出去，会被误算成"漏识别"。
- 本次数据在"重载 + 游戏运行"下取得，耗时数字比 E3 的回放结果更接近真实体感，但仍受当场负载影响（参考 E4）。

**废弃提示**：本次数据的"288 条新行"基于 D5 之前的旧去重逻辑；D5 之后预期会显著下降，需要重测并新增一条 E6。

## E1 · OCR 路线对比（同一张真实截图）

**条件**：`shots/Overwatch_q88jLuAM85.png`，737×421，守望聊天区，含中文/日文/韩文/英文混排，共 8 行文字。
机器空闲（仅有系统常驻进程）。

**命令**
```
python ocr_probe.py --image shots\Overwatch_q88jLuAM85.png --lang ko
python ocr_probe.py --image shots\Overwatch_q88jLuAM85.png --lang ko --rec-model ko5 --det-limit 320 --no-cls --repeat 3
python explore\ocr\ocr_simple.py shots\Overwatch_q88jLuAM85.png
```

**结果**

| 配置 | 识别情况 | 单次耗时 |
|---|---|---|
| probe 默认：ko4 + det 736 + 开 cls | 5 行中仅 2 行含韩文，其余乱码（如「不在脫天我道配史」），平均置信度 0.683 | 618 ms（推理 572） |
| 单头 ko5 + det 320 + 关 cls | 只韩文那行正确，其余退化成 `[re]:`、`[]`、`TAB` | **194 ms**（推理 157） |
| 双头集成 ko5 + v6（ocr_simple） | **8 行全对**，置信度 0.837~1.000 | **515 ms** |

**结论**
- 单一韩文模型不是"识别不准"，而是**字典所限根本吐不出别的文字**；多语种混排必须双头逐框择优。
- 择优判据用"结果里有没有谚文"，不能用置信度：日文模型读简体中文会给 0.972 的高分错字。
- 集成方案代价是可接受的（515 ms 级别），换来的是全覆盖。

**注意事项**
- probe 输出的「目标语种命中率」在多语种图上是误导性指标，别据此判断可行性。
- 之后复测同一命令得到 ~1000 ms，差别来自机器负载（E4），不是代码改动。

## E2 · 要不要加日文专用识别头（ja4）

**条件**：同上图；空闲负载。

**命令**
```
python ocr_probe.py --image shots\Overwatch_q88jLuAM85.png --lang ja --rec-model ja4 --det-limit 320 --no-cls
```

**结果**

| 模型 | 日文那行 | 置信度 | 副作用 |
|---|---|---|---|
| v6（现用双头之一） | `[Ire]:普段プレイしないなら、混ざるな` | 0.988 | — |
| ja4 | `[re]：普段プレイしないなら、混ざるな` | 0.944 | 丢了首字母 `I`、`:` 变全角；且把简体中文读成繁体错字（`頻道`/`平肘`/`臥伍`） |

**结论**：**不加 ja4**。v6 在日文行上本来就更准，加 ja4 只增加一次推理与一类误读风险。

**注意事项**：这是单张图的结论。若将来真机上日文识别率明显偏低，可重开 E2 复测，别凭"日文就该用日文模型"的直觉加。

## E3 · 半实时链路稳态（回放模式）

**条件**：静态图回放 + 人为造变化（`--sim-change-every`），无界面自测。
负载状态分两档：**轻载**（仅本进程）与**重载**（同时跑着 DSH Desktop / Steam / QQ 等）。

**命令**
```
python probe_live.py --replay shots\Overwatch_q88jLuAM85.png --sim-change-every 4 --heartbeat 4 --duration 9
python probe_live.py --replay shots\Overwatch_q88jLuAM85.png --sim-change-every 4 --duration 8 --dedupe-similar 0.85
```

**结果**

| 指标 | 轻载 | 重载 |
|---|---|---|
| 截屏（回放取帧） | 0.3~0.5 ms | 0.3~0.5 ms |
| 帧差 | 0.8~1.0 ms | 1.0~1.4 ms |
| 集成 OCR 单次 | 287~537 ms | 690~1254 ms |
| 跳过率 | 50% | 63%~70% |
| 实际循环 | 3.1 fps | 2.0~2.5 fps |

假新行（造变化遮住半行日文、导致同一行被读成 `段プレイしないなら` / `イしないなら` / `：こないなら` 等变体）：
不开抖动抑制 **17 条**新行（实际只有 8 条）→ `--dedupe-similar 0.85` 后 **15 条**。

**结论**
- 帧差这个闸门是划算的：~1.5 ms 的判断省掉 2/3~70% 的 OCR。
- 循环被 OCR 串行阻塞，实际只有 2~3 fps（目标是 4 fps），聊天滚动期间会漏帧。
- 近似去重能压掉一部分抖动噪声，但压不干净：同一行被遮挡一半时，输出与原文差异远超 15%。

**注意事项**：回放模式的"截屏"只是内存拷图，真实屏幕采集要慢得多（GDI/ImageGrab 抓窗口预计 10~30 ms），
所以**本表的截屏耗时不能代表真机**；真机数据要重测并新增 E5 之类的条目。

## E4 · 机器负载对 OCR 耗时的影响（元实验）

**条件**：同一脚本、同一张图、同一套模型，仅改变机器上是否有其它重负载进程。

**命令**
```
python explore\ocr\ocr_simple.py shots\Overwatch_q88jLuAM85.png      （连跑 3 次）
```

**结果**：空闲时 515 ms；机器上跑着 DSH Desktop（CPU 累计 300 s+）、steamwebhelper、QQ 时 966~1109 ms。

**结论**：**同一份代码的耗时能差 2 倍**。所以：
- 引用任何耗时数字都必须当场复测，不能拿历史数字当基准；
- 判断"够不够快"要看相对指标（跳过率、新行数是否对得上），别盯绝对毫秒；
- 真机测试时游戏本身会占 CPU/GPU，实测可能比我这边更慢，预算要留余量。

**注意事项**：这也是为什么本项目所有性能结论都标注了负载状态。
