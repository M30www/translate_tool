# 游戏内聊天实时翻译小工具 —— 可行性与设计分析

> 目标:在《守望先锋 2》(及同类游戏)中,把队友/对手的外语聊天(韩文/日文等)实时翻译成中文;
> 并让用户用中文输入、自动翻译后发回游戏聊天框。
>
> 本文重点:**反作弊边界**(第一约束) + **显示方式设计**(产品形态)。

---

## 0. 结论速览

**技术上完全可行,难度中等偏低。真正的风险不在技术,而在"用哪种手段"——手段选对了,风险可以从"很可能封号"降到"理论上存在但极低"。**

| 维度 | 评估 | 说明 |
|---|---|---|
| 技术可行性 | ✅ 高 | 截图 + OCR + 翻译 + 置顶窗口,全是成熟技术 |
| 工程难度 | 🟡 中 | 难点在 OCR 对游戏字体的适配,不在架构 |
| 反作弊风险 | 🟡 **取决于实现** | 纯外部方案≈低风险;注入/Hook 方案=必封 |
| 成本 | ✅ 极低 | 翻译按字符计费,一场游戏几分钱 |
| 学习价值 | ✅ 高 | 覆盖 Win32 窗口、屏幕采集、OCR、异步 IO、GUI |

**一句话结论**:把工具做成"**看屏幕的眼睛 + 自己的悬浮窗**",绝不碰游戏进程,就是一个安全且实用的项目。

---

## 1. 反作弊:项目的第一约束

### 1.1 核心设计原则:零接触(Zero-Touch)

> **不注入、不 Hook、不读内存、不改包、不自动化游戏行为。**

这个原则有个很好的性质:它同时是**最安全**的方案,也是**技术最简单**的方案。
所有"看起来很酷但危险"的手段(比如把译文直接画在游戏画面里)恰恰都是可以被反作弊抓到的。

判断某个技术是否可用,只需问一个问题:
**"我的代码有没有以任何形式触碰游戏进程,或者干预游戏收到的输入?"**
- 没有 → 安全区
- 有 → 危险区,必须换方案

### 1.2 技术手段红黄绿清单

| 手段 | 评级 | 原因与替代方案 |
|---|---|---|
| 屏幕采集(DXGI Desktop Duplication / Windows Graphics Capture / GDI BitBlt) | 🟢 安全 | 操作系统级 API,读的是显示器最终画面,与游戏进程零交互。OBS 就是这么录游戏的 |
| 自己的置顶透明窗口(WS_EX_TOPMOST + WS_EX_LAYERED + WS_EX_TRANSPARENT + WS_EX_NOACTIVATE) | 🟢 安全 | 只是 DWM 合成器里的另一个窗口,没有触碰游戏。Discord/Steam 覆盖之外,"纯外部置顶窗"是另一类东西 |
| 读写系统剪贴板 | 🟢 安全 | 与游戏无关 |
| 网络请求翻译 API | 🟢 安全 | 与游戏无关 |
| `RegisterHotKey` 注册全局快捷键 | 🟢 安全 | 官方 API,内核直接分发,不需要钩子 |
| 全局底层键盘钩子 `WH_KEYBOARD_LL`(用来"监听"回车键判断聊天框开了没) | 🟡 谨慎 | 正常软件(输入法、启动器)也用,但**键盘钩子正是外挂读取输入的标准手段**,容易撞上启发式检测。**建议改用 RegisterHotKey 或干脆不检测游戏状态** |
| `SendInput` 模拟按键(自动粘贴/自动发送) | 🟡 谨慎 | 单次、由人类按键触发,基本等同于无障碍辅助工具;但若实现成"自动开聊天框→粘贴→发送"的连招,就接近"宏/自动化操作"这条线了 |
| 进程内 DLL 注入、`SetWindowsHookEx` 挂进游戏 | 🔴 禁止 | 这是最经典的外挂注入手法,必被检测 |
| 图形 API Hook(Present / SwapChain / Vulkan Layer) | 🔴 禁止 | 绝大多数"内嵌覆盖层"外挂走这条路,反作弊的常驻检测目标 |
| `ReadProcessMemory` / 打开游戏进程句柄 | 🔴 禁止 | 读内存 = 作弊特征 |
| 网络封包解析/修改 | 🔴 禁止 | 已有大量封号先例 |
| 内核态驱动 | 🔴 禁止 | 除非你想做下一个 Vanguard |
| 自动瞄准/自动走位/任何游戏行为自动化 | 🔴 禁止 | 与翻译无关,不要顺手做 |

### 1.3 全屏 vs 无边框:一个被技术强行决定的结论

你提到"至少需要支持全屏窗口化"。实际情况比这更明确:

- **独占全屏(Exclusive Fullscreen)**:DWM 合成被绕过,任何**非注入**的置顶窗口都**不可能**显示在游戏之上。
  要在独占全屏上画东西,只能 Hook 图形 API —— 也就是唯一的办法正好是违法的办法。
- **无边框窗口化(Borderless Windowed)**:DWM 正常合成,置顶透明窗口可以正常覆盖显示。✅

**所以:无边框窗口化不是一个折中,而是这个项目唯一可行的显示模式。** 好消息是它同时也是最安全的那条路。

代价要说清楚:无边框窗口化相比独占全屏通常会多约 1 帧左右的延迟。守望先锋里可以打开
**NVIDIA Reflex** 和 **降低缓冲(Reduce Buffering)** 来补偿,大多数玩家感知不到差异。

> **如果用户有第二块显示器 —— 那干脆不要覆盖游戏。** 把翻译面板放在副屏,游戏保持独占全屏、
> 零延迟、零覆盖风险,体验反而最好。这应该是"零妥协方案",值得作为一等公民支持。

### 1.4 出方向(发消息)的风险细节

真正需要小心的是"把译文送回游戏"这一步。三个层次:

| 方案 | 风险 | 用户体验 | 建议 |
|---|---|---|---|
| **A. 只复制到剪贴板 + 提示"按 Ctrl+V"** | 🟢 极低 | 需要手动 3 个键(回车开聊天 → Ctrl+V → 回车发送) | **默认方案** |
| **B. 一键:工具自动聚焦回游戏并发送 [回车][Ctrl+V][回车]** | 🟡 低但非零 | 一个快捷键搞定 | 可选功能,**默认关闭**,设置里明确写清风险 |
| **C. 逐字符模拟键盘输入译文** | 🟡 低但非零 | 慢,且 CJK 字符注入兼容性差 | 不推荐,直接用剪贴板 |

**为什么 B 的风险仍然"低"**:服务端看到的就是"一个玩家打开了聊天框、粘贴了一段文字、发送"——
和真人操作**在数据上完全一致**,没有任何作弊特征。而暴雪的封禁红线是"自动化游戏行为/获得竞技优势",
翻译聊天不构成任何一项。
**为什么不是"零"**:因为所有反作弊的行为模型都可能把"精确到毫秒的固定按键序列"判为宏。
人类手动按是不可能有这个特征的。

> **务必实测的点**:守望先锋的聊天输入框能否接受 `Ctrl+V` 粘贴、以及能否正确显示韩文/日文。
> 这是纯游戏行为验证,不涉及作弊,但决定出方向方案的可行性。**建议在 Phase 0 就手动测一遍。**

### 1.5 关于《英雄联盟》和其他游戏

- **LOL**:Riot 现在 Windows 端强制 **Vanguard(内核级反作弊)**,比暴雪的 Warden 激进得多。
  上面"零接触"原则依然适用,但要更保守:不要用全局钩子,不要尝试任何注入。
  Riot 有官方"第三方应用"白名单机制(Blitz、Porofessor 那类),走的是官方 Client API——
  但**官方 API 不提供聊天内容**,所以聊天翻译仍然只能靠 OCR。
- **通用性**:这套架构(采集 → OCR → 翻译 → 外部覆盖层)对任何"无边框窗口化 + 有聊天框"的游戏都通用,
  只需要调整聊天区域坐标和字体预处理参数。

### 1.6 我对封号风险的诚实评估

置信度说明:暴雪**不公开** Warden 的内部实现和判定阈值,以下是工程推断,不是官方承诺。

- 采用"零接触"方案(第 1.2 节全部绿色项 + 出方向方案 A),**我判断封号风险极低**,理由:
  1. 没有任何可被检测的作弊特征(无注入、无内存访问、无 Hook、无游戏行为自动化);
  2. 服务端能看到的只是正常的聊天消息;
  3. 从未有"仅因运行了一个屏幕翻译悬浮窗而被封"的公开案例。
- 零风险不存在。EULA 对"第三方软件"的措辞是宽泛且**由官方自由裁量**的,理论上他们可以封任何东西。
- **降低残余风险的具体做法**:
  - 个人自用,**不分发、不收费、不宣传**——被关注的概率与传播度正相关;
  - **先用小号/测试账号跑一两周**,确认无异常再上主号;
  - 出方向默认用方案 A(手动粘贴),不默认开启自动化;
  - 不要以管理员权限运行(没必要,且更容易被盯上);
  - 保留工具运行日志,万一出问题有申诉依据。

## 2. 显示方式设计(产品形态)

你问的"直接覆盖原对话框,还是别处显示"——这是这个项目最重要的产品决策。

### 2.1 三个方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 原地覆盖替换原文** | 用一块半透明色块盖住游戏原聊天文字,在上面画译文 | 最沉浸、视觉最干净 | ① 游戏聊天背景是**动态游戏画面**,盖纯色块很突兀;② 聊天文字几秒后自动淡出,你的译文也得跟着淡出,**消息一消失用户就看不到了**;③ 聊天框位置/字体/换行随分辨率、UI 缩放、语言变化,极其脆弱;④ 玩家发言重叠时无法对应 | ❌ **不做 MVP**,可作为后期"沉浸模式"可选实验 |
| **B. 悬浮翻译面板(推荐)** | 在聊天区旁边/上方显示一个半透明圆角面板,列出"原文 + 译文" | ① 不跟游戏渲染博弈,稳定;② **自带历史记录**;③ 可显示说话人、时间、颜色区分敌我;④ 可点击复制 | 会遮挡一小块画面(可调透明度/位置/自动淡出) | ✅ **主方案** |
| **C. 第二屏 / 普通窗口** | 工具就是个普通置顶窗口,用户拖到副屏 | 零覆盖风险,零延迟妥协,可做大做复杂 | 需要双显示器 | ✅ **一等公民**,有副屏就直接用 |

### 2.2 关键洞察:面板 = 聊天历史,而不只是"翻译结果"

游戏的聊天文字会在几秒后淡出消失,等你盯着翻译看完,原文已经没了。如果译文也跟着消失,
你会在"消息消失"和"翻译延迟"之间反复丢失信息。

**所以面板应该做成一个持续滚动的日志,而不是一次性气泡:**

```
┌─────────────────────────────┐
│ 🇰🇷 [Kim] 힐 좀 줘           │  ← 原文(小字、灰色)
│ 💬 [Kim] 给我点治疗          │  ← 译文(大字、白色)
│ 🇯🇵 [Sato] ナイス！          │
│ 💬 [Sato] 打得好!            │
└─────────────────────────────┘
```

这个设计顺便解决了一个原方案没有的问题:**用户回头还能看到 10 秒前说了什么**。
它比"原地替换"更实用,而且实现简单得多。

### 2.3 具体视觉规格建议

- 位置:默认贴在聊天区上方(守望先锋聊天区默认在左下角),可拖动、可记忆位置;
- 尺寸:宽度 ~520px,高度 ~260px,最多显示 6~8 条,超出滚动淘汰;
- 样式:深色半透明(背景 `rgba(10,10,14,0.55)`)、圆角 10px、无边框、右侧 1px 强调色条;
- **点击穿透默认关闭**(方便复制文本),但提供一个"锁定/穿透"切换键——穿透后鼠标点击会落到游戏上;
- 自动淡出:无新消息 N 秒后整体降到 25% 不透明度(不是消失),鼠标悬停恢复;
- 快捷键:
  - `Ctrl+Alt+T` 显示/隐藏面板
  - `Ctrl+Alt+O` 开关点击穿透
  - `Ctrl+Alt+I` 唤出中文输入框
  - `Ctrl+Alt+P` 暂停/恢复 OCR(比赛关键局想全神贯注时)

### 2.4 出方向的交互设计

难点:用户要在工具里打中文,工具窗口就必须获得焦点;而游戏聊天框一旦失焦,**守望先锋很可能直接关闭聊天输入**。
所以不能"在游戏聊天框里打字",只能走"工具里打完 → 送回游戏"。

**推荐交互(方案 A,安全)**:
1. 按 `Ctrl+Alt+I` → 弹出一个小输入框(自动聚焦,支持中文输入法);
2. 输入中文,按 `Enter` → 立刻翻译,并**自动复制到剪贴板**;
3. 面板高亮提示:`已复制,按 回车 → Ctrl+V → 回车 发送`;
4. 工具自动隐藏并**把焦点交还给游戏**(这一步很关键,否则你按回车游戏收不到)。

**可选交互(方案 B,一键)**:同样的流程,但第 3 步由工具代劳,自动发 `[Enter][Ctrl+V][Enter]`。

**必须注意的细节**:游戏聊天有**单条消息长度上限**,翻译结果过长时会被截断,
需要实现"按长度自动切分成多条发送"。这个上限得实测确认。

## 3. 技术链路拆解

```
[屏幕固定区域] --采集--> [图像] --预处理--> [OCR] --语言判定--> [翻译] --缓存--> [悬浮面板]
                                                                    ↑
                                              [中文输入框] --翻译--> [剪贴板/模拟按键] --> 游戏
```

### 3.1 屏幕采集

只需采集聊天区那**一小块矩形**(约 400×180),不需要整屏。

| 方案 | 说明 | 推荐 |
|---|---|---|
| `Graphics.CopyFromScreen`(GDI BitBlt) / `mss` | 最简单,小块区域 2~5 fps 开销可忽略 | ✅ **MVP 首选** |
| `Windows.Graphics.Capture`(C# 原生投影) / `windows-capture` | 现代 API,HDR 处理更好 | ✅ 正式版首选 |
| `dxcam`(DXGI Desktop Duplication) | 极快、极低 CPU,适合提高帧率 | 后期可选 |

无边框窗口化下三者都能正常采集到游戏画面。

### 3.2 OCR —— 项目最大的技术风险点

游戏文字的特点:字号小、白色带描边、背景是动态高对比画面。预处理非常关键。

| 方案 | 中/日/韩 效果 | C# 侧 | Python 侧 | 推荐 |
|---|---|---|---|---|
| **PP-OCR 系列模型**(RapidOCR 系) | 好 | **RapidOcrNet**(net8.0,12 MB,AOT 兼容,仅依赖 SkiaSharp) | `rapidocr-onnxruntime`(无 torch) | ✅ **首选** |
| PaddleOCR 原生推理 | 最好 | **PaddleOCRSharp**(net8.0,69 MB,含 `Paddle.Runtime.win_x64`) | `paddleocr`(需 paddlepaddle,较重) | 备选 |
| Windows.Media.Ocr(WinRT 内置) | 中等 | 原生投影,零依赖 | 需 `winsdk` 绑定 | ⚠️ **实测本机只有 en-gb / zh-cn 引擎,无韩日**,需装语言包(管理员),且对游戏小字不佳 |
| Tesseract | CJK 明显偏弱 | — | — | ❌ 不推荐 |
| 多模态大模型(直接发裁剪图) | 最好,game slang 和糊字都能处理 | HTTP + base64 | `pip install openai pillow` | 🔁 值得对比的替代路线,也可用来验证概念是否成立 |

> **关键前提**:RapidOcrNet 与 Python 的 `rapidocr` **跑的是同一套 PP-OCR ONNX 模型、同一套预处理**
> (RapidOcrNet 甚至专门提供 `PythonCompat` 预设来对齐 Python 版行为)。
> 所以 **"OCR 认不认得出游戏里的韩文"这个最大风险,与语言选择无关** —— 换语言不会改变识别率。

**预处理建议(能显著提升准确率)**:
1. 放大 2~3 倍(Lanczos)——小字号是 OCR 的头号杀手;
2. 灰度化 + 对比度拉伸;
3. 游戏聊天是"白字 + 黑描边",可以对亮度通道做阈值化,把动态背景压掉;
4. 裁掉头像/分割线等噪声区域。

### 3.3 语言判定:别用统计模型,用 Unicode 区块

游戏聊天很短(常常就一两个词),统计式语言识别很不靠谱。但日韩文有天然特征:

```csharp
static string GuessLang(string s)
{
    if (s.Any(c => c is >= '\uAC00' and <= '\uD7A3' or >= '\u1100' and <= '\u11FF'))
        return "ko";   // 韩文音节 / 字母
    if (s.Any(c => c is >= '\u3040' and <= '\u30FF'))
        return "ja";   // 平假名 / 片假名
    if (s.Any(c => c is >= '\u4E00' and <= '\u9FFF'))
        return "zh";   // 纯汉字:中文,或日文汉字(歧义时按上下文/历史判定)
    return "en";
}
```

免费、零延迟、对短文本比任何 LID 库都准。**这是个非常划算的小技巧。**

### 3.4 翻译后端

| 方案 | 中↔日/韩 质量 | 游戏黑话 | 成本 | 备注 |
|---|---|---|---|---|
| **LLM(DeepSeek / OpenAI 等)** | 好 | ✅ 最好,能理解 "diff"、"ns"、"gg"、英雄名 | 每条约 ¥0.0002,可忽略 | ✅ **首选**,还能顺带做语气/缩写还原 |
| DeepL API Free | 很好 | 一般 | 50 万字符/月免费 | ✅ 稳定备选 |
| Google Cloud Translation | 好 | 一般 | ≈$20/百万字符 | 备选 |
| Naver Papago | 韩→中最佳 | 一般 | 有免费额度 | 韩语专精时可选 |
| `googletrans`(非官方) | 一般 | 差 | 免费 | ⚠️ 随时失效,别用在正式版 |

**强烈建议加的两个东西**:
1. **术语表(glossary)**:把英雄名、地图名、常用缩写固定映射(`"diff"→"实力差距"`、`"ns"→"打得好"`),
   翻译质量提升最明显、成本最低的一步;
2. **翻译缓存**:游戏聊天重复率极高(`gg`、`heal me`、`push`),内存 LRU 缓存能砍掉大半 API 调用,
   同时把常见消息的延迟从 ~500ms 降到 ~0ms。

### 3.5 延迟预算

| 环节 | 耗时 |
|---|---|
| 区域截图 | 5~15 ms |
| 变化检测(无变化则跳过) | < 2 ms |
| OCR | 50~200 ms |
| 翻译(网络) | 200~800 ms |
| 缓存命中 | ~0 ms |
| **合计** | **约 0.3~1.0 秒** |

完全可接受。加上缓存,常用短语几乎瞬时。

### 3.6 触发策略(省算力、防漏消息)

不要无脑每秒 OCR 十次。推荐:
- 以 3~5 fps 采集,**帧差小于阈值就跳过 OCR**;
- 检测到新文本 → OCR → 与上一条做相似度去重(避免同一句话被反复翻译);
- 只在聊天区域出现"新行"时才调翻译 API。

## 4. 技术栈建议

**推荐:C# / .NET 8 + WPF,OCR 用 RapidOcrNet 打底、PaddleOCRSharp 备选。**

### 4.1 为什么是 C#

本机环境已经就绪,无需额外安装:

```
dotnet SDK             8.0.200
WindowsDesktop 运行时  8.0.2      (WPF / WinForms 可用)
Windows                11 build 26100 (24H2)
```

真正的理由是**这个项目需要的三样东西,恰好都是 Windows 原生接口**:

| 需要什么 | C# 怎么拿 | Python 怎么拿 |
|---|---|---|
| 屏幕采集 | `Windows.Graphics.Capture`(WinRT)。TFM 设为 `net8.0-windows10.0.19041.0` 即为**原生投影**,零胶水 | 需 `winsdk` / `winrt` 第三方绑定,或退回 `mss`(GDI) |
| 半透明 + 点击穿透悬浮窗 | WPF `AllowsTransparency` + P/Invoke `WS_EX_LAYERED` / `WS_EX_TRANSPARENT` / `WS_EX_NOACTIVATE`;Win11 24H2 还可一个 `DWMWA_SYSTEMBACKDROP_TYPE` 拿到**系统级 Acrylic 亚克力背景** | Qt 的 `WindowTransparentForInput` 同样好,但亚克力模糊要自己做 |
| 全局热键 / 剪贴板 / SendInput | 标准 P/Invoke | ctypes,同样可以 |

附加优势:
- **最终产物**:`dotnet publish --self-contained` 出单个 exe,冷启动快,无需用户装运行时;
- **规避 PyInstaller 的杀软误报**:一个"截屏 + 模拟按键"的工具被 PyInstaller 打包,正好凑齐杀软启发式的敏感特征。
  不会导致封号,但白白多一层麻烦;
- `HttpClient` + `System.Text.Json` + `async/await` 写"采集 → OCR → 翻译"流水线,比 Python 的异步干净;
- 强类型 + VS/Rider,重构和调试舒服。

### 4.2 诚实的另一面:Python 赢在哪

1. **探索期速度**:Phase 0 试不同预处理参数时,Python 里 `pip` + numpy + Pillow 随手改随手跑。
   但注意 —— 因为用的是**同款模型**,这个实验结论是通用的,不会因换语言而改变。
2. **多模态大模型兜底**:Python 里 20 行搞定;C# 里是纯 HTTP + base64,不难但示例少。
3. **将来接本地翻译模型**(llama.cpp / transformers)时,Python 生态厚得多。

**什么时候应该反过来选 Python**:如果做这个项目的主要目的是**学 Python**,或者想**先花一下午穷举式验证 OCR 可行性**再决定是否认真做。
这两个都是正当理由 —— 只是"C# 的 OCR 生态不行"不是理由,经核实它并不成立。

### 4.3 为什么不是 C++

会手写 WinRT interop + ONNX Runtime 胶水 + JSON 库,换来的是**这个场景根本不需要的性能**。
瓶颈在模型推理,而模型推理在三种语言里都是同一份 C++ 后端。复杂度不会转化成任何用户可见的收益。

### 4.4 组件选型

| 组件 | 选型 | 备注 |
|---|---|---|
| 框架 | .NET 8 + WPF | TFM:`net8.0-windows10.0.19041.0`(为了 WinRT 投影) |
| OCR | **RapidOcrNet** | 12 MB,AOT 兼容,仅依赖 SkiaSharp(已剥离 OpenCV / System.Drawing) |
| OCR 备选 | PaddleOCRSharp | 69 MB,含原生 `Paddle.Runtime.win_x64` |
| 采集 | `Windows.Graphics.Capture` | 或先用 `Graphics.CopyFromScreen` 验证 |
| 翻译 | LLM API / DeepL | `HttpClient` + `System.Text.Json` |
| 热键 | `RegisterHotKey` | 不用钩子,安全 |
| 剪贴板 / 输入 | `Clipboard` + `SendInput` | — |
| 打包 | `dotnet publish --self-contained -p:PublishSingleFile=true` | 别追 NativeAOT |

**两个必须注意的坑**:

1. **RapidOcrNet 默认自带的是 latin 模型,读不了韩日文。** 需要下载
   `korean_PP-OCRv5_rec_mobile.onnx` + `ppocrv5_korean_dict.txt`(日文同理)。
   **rec 模型和 dict 文件必须配对,不配对会输出乱码。**
   国际服可能同时冒出韩文、日文、英文,更省事的做法是直接用 **PP-OCRv6 多语言模型**。
2. **别为 NativeAOT 折腾**:WinRT 投影与 AOT 存在冲突,`self-contained + ReadyToRun` 单文件已足够。

### 4.5 性能

不是瓶颈。OCR 算力在同一份 C++/ONNX 后端上,3~5 fps 识别一小块聊天区,CPU 占用可忽略。

## 5. 分阶段路线图

每一步都能独立跑起来看到效果,不会出现"写了三天什么都没有"的情况。

| 阶段 | 内容 | 产出 | 预估 |
|---|---|---|---|
| **Phase 0** | 概念验证脚本:截取固定矩形 → OCR → 打印到控制台。**同时手动测试:能否往守望聊天框粘贴韩文、消息长度上限是多少** | 确认 OCR 能不能认出游戏字,确认粘贴可行 | 半天 |
| **Phase 1** | 接上翻译 + Unicode 语言判定 + 控制台输出中韩对照 | 命令行版可用 | 半天 |
| **Phase 2** | WPF 半透明置顶面板,显示"原文/译文"滚动历史 | **核心体验成型**,已经能用了 | 1~2 天 |
| **Phase 3** | 中文输入框 → 翻译 → 剪贴板 → 焦点交还游戏 | 双向闭环 | 1 天 |
| **Phase 4** | 术语表、翻译缓存、区域可视化框选、配置持久化、热键 | 好用 | 1~2 天 |
| **Phase 5** | 可选:一键发送(方案 B)、副屏模式、原地覆盖实验 | 进阶 | 按需 |
| **Phase 6** | dotnet publish 单文件发布 + 开机自启 | 成品 | 半天 |

**先做 Phase 0 的理由**:整个项目唯一的真实不确定性是"**OCR 能不能稳定认出游戏里的小字号韩文/日文**"。
先用 20 行代码验证这一点,再决定投入多少。如果 Tesseract 不行就换 RapidOCR,如果 RapidOCR 也不行就换多模态大模型。

## 6. 风险登记表

| 风险 | 等级 | 对策 |
|---|---|---|
| 因第三方软件被封号 | 🔴 高影响 / 🟢 低概率 | 严守"零接触"原则;默认手动粘贴;小号先行;个人自用不分发 |
| OCR 认不准游戏小字 | 🟡 中 | Phase 0 先验证;放大 + 阈值化预处理;备选多模态大模型 |
| 独占全屏下无法覆盖 | 🟡 中(已确定) | 无边框窗口化,或用副屏。这是技术必然,不是 bug |
| 聊天文字几秒后消失导致漏翻 | 🟡 中 | 面板做历史日志 + 高帧率采集 + 变化检测 |
| 翻译 API 收费/限流/失效 | 🟢 低 | 缓存 + 术语表 + 多后端可切换 |
| 游戏更新导致聊天区域坐标变化 | 🟢 低 | 提供可视化框选 + 配置持久化,不用重新编译 |
| 聊天消息长度上限导致截断 | 🟢 低 | Phase 0 实测上限,按长度切分发送 |
| 隐私:聊天内容发送到第三方 API | 🟢 低 | 本地缓存可关;可换本地小模型 |
