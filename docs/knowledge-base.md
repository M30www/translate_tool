## 1. 数据流全景

```
屏幕区域
  │
  ├─[1] 帧差闸门 ──(没变化就跳过,省 80% OCR)
  │
  ├─[2] 集成 OCR ──(ko5 韩文头 + v6 多语头,逐框择优)
  │
  ├─[3] 行重组 ───(丢半行 → 横向拼碎片 → 纵向拼续行 → 排序)
  │
  ├─[4] 消息判定 ──(归一化键 + 可见窗口 + 残片抑制 + 补全更新)
  │
  ├─[5] 分类 ──────(按文字颜色区分聊天 / 系统提示 / UI)
  │
  └─[6] 翻译 ──────(独立线程:过滤 → 只翻正文 → 缓存 → 引擎)
        │            采集/OCR 只管投递,队列 maxsize=64 满了丢最旧
        └─[7] 输出(控制台 / 日志 JSON / Markdown 对照表 / 未来悬浮窗)
```

对应文件：`probe_live.py`（1–4、日志）、`explore/ocr/ocr_simple.py`（2–3）、`chat_text.py`（4）、
`analyze_log.py`（判读）、`translate_text.py` + `translate_log.py`（6）。

## 2. 各阶段判据与参数

### [1] 帧差闸门（`probe_live.py`）

| 项 | 值 | 依据 |
|---|---|---|
| 缩图尺寸 | 160×90 灰度 | 原分辨率比较会被抗锯齿噪声淹没 |
| 单像素"变了"阈值 | 亮度差 > 16 | 同上 |
| 触发 OCR 的变化比例 | ≥ 0.2% 像素 | 实测静帧可省掉 68~82% 的 OCR |
| 目标帧间隔 | 0.25 s（4 fps） | 实际 2.4~3.3 fps，被 OCR 阻塞 |

### [2] 集成 OCR（`ocr_simple.py`）

| 项 | 值 | 依据 |
|---|---|---|
| 识别模型 | ko5（韩文）+ v6（52 语种），检测/分类共用 | 单韩文模型**永远吐不出韩文以外的字**（字典所限） |
| 逐框择优判据 | 结果含谚文 → 采信 ko5，否则 v6 | **不能用置信度**：日文模型读简体中文会给 0.972 的错字 |
| `det_limit_side_len` | 320 | 包内默认 736 会把小图放大 3.7 倍，又慢又不准 |
| `use_cls` | False | 游戏文字不会倒置，省一次推理 |
| `text_score` | 0 | 否则两模型返回的框集合不同，合并会冒出垃圾行 |
| 单次耗时 | 300~1000 ms | **随机器负载能差 2 倍**（见 E4） |

### [3] 行重组（三步，顺序不可调换）

| 步骤 | 判据 | 参数 | 为什么是这个顺序 |
|---|---|---|---|
| `drop_clipped` 丢半行 | 框高 < **70%** 中位行高 | `--min-height-ratio` | 先丢，免得半行参与后面的合并 |
| `merge_fragments` 横向拼 | 中心线差 ≤ 半行高 且 水平间距 ≤ 0.8 行高；**收敛式**反复合并 | `gap_ratio=0.8` | 检测框会把一行切成多段；单趟贪心会漏合（实测 3 段只合 2 段） |
| `join_wrapped` 纵向拼 | 无 `[昵称]` 前缀 + **与上一行同色** + y 差 ≤ 40 px | `LINE_GAP=40` | 游戏会把长消息折成多行；同色是安全前提（系统提示也无前缀） |

细节规则：
- 横向合并时，组内**有效字符 ≤1 的段丢弃**（左侧头像区常被误检成 `や`），置信度取 **max**（前后缀碎片分低）。
- 前缀正则 `PREFIX`：行首（容忍 ≤8 个噪声字符）出现 `[昵称]` 即视为"新消息起点"，带不带冒号都算（系统消息是 `[辛铂宵] 退出了…`）。
- 排序：`(round(y/12), x)` —— RapidOCR 返回顺序不代表视觉顺序。

### [4] 消息判定（`probe_live.emit`）

核心键：`chat_text.norm_key(text)`
> 剥掉行首到第一个冒号的前缀（≤24 字符内）→ 只保留字母数字（中文/韩日文在 Python 里都算 alnum）→ 折叠整句重复（`5초만기다려×3` → ×1）。
> 一次剥掉空白、标点、`※·▲[]` —— 手列符号表必然漏。

| 规则 | 状态容器 | 行为 |
|---|---|---|
| 可见窗口 | `seen`: key → 最后可见时刻 | 6 s 内出现 = 不是新消息（挡住漏读一帧） |
| 重报抑制 | `reported`: key → 最后报出时刻 | 120 s 内不再报 |
| 残片抑制 | `history`: 最近 40 条已报 `(key,text)` | 无前缀 且 key(≥4) 是某条已报 key 的**子串** → 不报（那条完整消息已展示过） |
| 补全更新 | 同上 | 新 key **包含**某条已报 key(≥4) → 标 `↻`、写 `updates` 字段、**不计入新行** |
| 残片标记 | — | 无 `[昵称]` 前缀 → 事件写 `partial: true` |

### [5] 颜色分类

| 类型 | 实测颜色 | 说明 |
|---|---|---|
| 队伍聊天 | 青 `#00A2E0 ~ #00B3F0`（归一后约 `#00AEE9`） | 玩家消息，是翻译的主要对象 |
| 系统消息/警告 | 橙 `#C36800`、亮黄 `#EDCA00` | 限流提示、好友动态、退场提示 |
| UI 提示 | 灰蓝 `#2C82A1` | `[队伍] 按下TAB切换频道` |
| 输入法状态 | 白 `#ECECEC` | `中` |

取色方法：框内**最亮 12% 像素求均值**（字形笔画色，不含背景）。比较时按 `color_key`（48 级量化）入桶，
因为同一类文字每帧会抖 ±10。

> 注意：颜色目前只用于**统计与续行合并**，还没有用于过滤消息。
> 且频道色会随频道变化（比赛/私聊未采样），所以不要硬编码 `#00AEE9`。

### [6] 翻译（`translate_text.py` / `translate_log.py`）

| 环节 | 规则 |
|---|---|
| 输入过滤 | 只留**频道色**的行（自动 = 成员最多的色簇，可用 `--chat-color` 指定）；`norm_key` 长度 ≥2；中文不翻（`guess_lang`） |
| 送翻内容 | **只送正文**，`[昵称]:` 前缀原样拼回显示（翻了没意义，还会把冒号改成全角） |
| 缓存 | `cache/translate_<engine>.json`，键 = `norm_key`（与去重同源，天然抗抖动）；原子替换写入；`save_every=20` + **收尾显式 save**（否则最后一批会丢） |
| 引擎 | `echo`（回显）/ `free`（自动探测）/ `google` / `mymemory` / `llm`（OpenAI 兼容） |
| LLM 批量 | 每请求最多 8 条；`temperature=0.2`；要求返回 JSON 数组；**长度不符则整批降级**（绝不允许按顺序硬配，会把 A 的译文配给 B） |
| 免费引擎 | 逐条请求 + 0.2~0.3 s 延时（不支持批量，防限流） |
| 术语表 | **只对 LLM 生效**；免费接口不支持自定义术语 |
| 实时通道 | `probe_live.py --translate`：投递到 `LiveTranslator` 后台线程；批量窗口 0.25 s / 最多 4 条；队列满丢最旧；退出前排空 |
| 颜色过滤（实时） | 只翻"频道色"的行；颜色按**距离 ≤40 聚类**比较（精确 hex 或细量化桶会误杀，踩过） |
| 缓存版本 | 键前缀 `CACHE_VERSION`：**改了送翻口径必须升版本**，否则旧值被误命中（踩过） |

## 3. 概念词典（读日志/代码前先看这个）

| 词 | 含义 |
|---|---|
| **norm_key** | 归一化判据。去重、缓存都用它。能穿透昵称前缀与标点抖动 |
| **行位** | 检测框在区域内的 y 坐标（事件里的 `y`），用来判断是否同一行 |
| **抖动簇** | 同一条消息被读成多个近似变体（如 `普段` / `段ぷ`），`analyze_log` 按相似度 0.80 聚类统计 |
| **partial** | 该行没有 `[昵称]` 前缀 → 可能是头部被裁的残片，也可能是系统提示 |
| **updates** | 本次报出的文本包含某条已报消息 → 是同一条的更完整版本，应替换而非新增 |
| **频道色** | 该频道玩家聊天文字的颜色；系统提示不是这个颜色 |
| **半边行** | 被聊天视口裁掉一半的行（框高明显偏小），必然读错，直接丢 |
| **OCR 产出率** | 触发了 OCR 但没产出新行的比例。低 = 帧差阈值偏松（画面在动但聊天没变） |

## 4. 参数速查

| 参数 | 默认 | 作用 | 什么时候调 |
|---|---|---|---|
| `--min-score` | 0.75（写在 `run_live.bat`） | 低于此置信度的行丢弃 | 误读碎片多 → 调高；真实短句被吞 → 调低 |
| `--min-height-ratio` | 0.7 | 框高低于中位数此比例 = 没翻译价值，丢弃 | 换游戏/分辨率后重测 |
| `--threshold` | 0.002 | 帧差触发阈值 | 跳过率太低（画面一直动）→ 调高 |
| `--interval` | 0.25 | 目标帧间隔 | 想更快看画面 → 调小（但 OCR 是瓶颈） |
| `--visible-ttl` | 6.0 | "还在屏幕上"的判定窗口 | 滚动快导致重复报 → 调大 |
| `--recent-ttl` | 120 | 同一条消息多久内不重报 | 想看到重复发送的同一句 → 调小 |
| `--heartbeat` | 10 | 心跳间隔（0=关） | 嫌吵就 0 |
| `--no-join-wrapped` | 关（即默认合并） | 关掉纵向续行合并 | 做 A/B 对比时 |
| `--no-merge` | 关 | 关掉全部行重组 | 排查"是不是合并搞错了" |
| `--expect` (analyze) | 无 | 用测试句文件做召回核对 | 每次真机测试都建议带 |
| `--engine` (翻译) | `free` | 翻译引擎 | 正式质量 → `llm` |
| `--translate` | 关 | 开启实时翻译线程 | 想看实时译文时（`run_live_translate.bat` 已带） |
| `--translate-chunk` | 4 | 每批合并翻几条 | 免费引擎调小（首条更快）；LLM 可调大（省往返） |
| `--translate-all` | 关 | 不按颜色过滤 | 调试时确认某行到底有没有被送翻 |
| `--limit` (翻译) | 0 | 最多翻几条 | 先花 20 条试水 |

## 5. 已知限制（按影响排序）

| # | 现象 | 原因 | 现状处理 | 出路 |
|---|---|---|---|---|
| 1 | 同一帧里文本完全相同的两条消息只报一条 | 归一化键相同 | 接受（多为刷屏） | 需要时用 `(key, 行位)` 组合键 |
| 2 | 同一条长消息可能报两次（2 行版 + 3 行版） | 增量识别，文本不同 | 后者标 `updates` | UI 层落地"替换已显示条目" |
| 3 | 残片**先**出现时挡不住重复 | 子串抑制要求完整版已在历史 | 只能靠 `updates` 事后补 | 同上：产品层回填 |
| 4 | 两条不同消息被横向合并后，可能误判成 `updates` | 判据是文本包含关系 | 不丢内容，语义略偏 | 收紧为"必须同前缀/同颜色" |
| 5 | 快速滚动可能漏帧 | 串行循环 2~3 fps | 数据未证实是主要矛盾 | 需要时做采集/OCR 解耦 |
| 6 | 免费引擎译不准黑话/英雄名、英文短句原样返回 | 第三方通用接口的能力边界 | **已知且接受**：本轮只验证链路能否跑通（E9），**不为它做任何优化** | 换 LLM（代码已就绪，只换 `--engine llm` + 三个环境变量） |
| 7 | 免费引擎实时约 **1.5~3 s/条**，批量 4 条约 6~12 s，体感迟钝 | 免费接口网络 + 限速 | 已用线程隔离，不拖慢采集（E10/E11） | 换 LLM；或调小 `--translate-chunk` |
| 8 | 真机下**译文严重迟到**（p50 11.8 s / p95 26.1 s），出译文时消息已滚走 | 队列没满→从不丢弃；单线程串行 + 引擎慢 → 延迟累积（E11） | 现状；已确认需"过期丢弃" | 加入队超过 N 秒即放弃（`--translate-max-age`），把"迟到"变成"不浪费" |
| 9 | 真机 `--threshold=0.2%` 下 OCR 产出率仅 17%（大量白跑） | 真实对局画面持续在动 | 见 E11 | `--threshold` 提到 0.005~0.01；或缩小框选区域 |
| 10 | 首帧混进队伍列表（`IR1S` / `重装`） | 框选左边界过宽 | 见 E11 | 框选时左边界右收，只留聊天正文 |
| 7 | 系统提示/UI 元素仍在翻译候选里 | 颜色过滤尚未默认启用 | 手动 `--chat-color` | 定下频道色规则后默认开 |
| 8 | `나려` 之类碎片被翻成 `Narrying` | 垃圾进垃圾出 | 靠 `--min-score` 拦截 | 输入侧继续收紧 |

## 6. 排障手册

| 症状 | 先查什么 |
|---|---|
| 一条新行都没有 | 框选区域是否框到聊天区；`--threshold` 是否太高；画面是否静止 |
| 同一句话被反复报 | 看 `analyze_log` 的「抖动簇」：若簇多且变体差异大，说明 `norm_key` 剥不掉（前缀格式变了？） |
| 大量乱码短行 | ① 区域上下边缘是否切到半行（看 `y` 是否集中在边界）② `--min-score` 太低 |
| 长句被拆成几条 | 是否 `--no-join-wrapped`；续行颜色是否与首行不同（不同色不会合并，这是设计） |
| OCR 变慢一倍 | 机器负载（见 E4），不是代码问题，当场复测确认 |
| 翻译全失败 | `--engine free` 看探测结果；`llm` 则检查 `DS_LLM_API_KEY` |
| 译文里出现 `⟨未翻⟩` | 引擎把原文照抄了（常见于英文短句/黑话），不是管道问题，换 LLM 才治本 |
| 术语表没生效 | 免费引擎不支持术语表，只有 `llm` 生效 |
| 中文被送去翻译 | `guess_lang` 判错；检查该行是否混排了拉丁字母 |
